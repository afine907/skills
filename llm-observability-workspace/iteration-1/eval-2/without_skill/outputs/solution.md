# Agent 统一监控仪表盘 — 指标体系与设计方案

## 1. 概述

本方案为 5 个生产环境 Agent 构建统一监控仪表盘，覆盖**健康状况**、**成本消耗**、**质量趋势**三大核心维度。方案采用分层指标体系，从全局概览逐层下钻到单 Agent 细节，支持实时告警与历史趋势分析。

### 设计原则

- **全局优先**：老板打开仪表盘第一眼看到整体健康评分，3 秒内判断是否需要介入
- **分层下钻**：全局 → Agent 级别 → 单次请求级别，逐层深入
- **可行动**：每个指标都对应明确的阈值和告警动作
- **成本敏感**：LLM 调用成本是核心约束，必须精确到模型/Agent/用户维度

## 2. 指标体系

### 2.1 一级指标：全局健康概览（Executive View）

| 指标名称 | 计算方式 | 展示形式 | 刷新频率 |
|---------|---------|---------|---------|
| **综合健康评分** | 加权平均：可用性 30% + 延迟 20% + 成功率 25% + 质量分 25% | 0-100 分大字牌，绿/黄/红三色 | 30s |
| **活跃 Agent 数** | 过去 5 分钟有请求处理的 Agent 数量 | 5/5 在线状态 | 实时 |
| **今日总请求数** | 所有 Agent 今日请求合计 | 数字 + 环比变化箭头 | 1min |
| **今日总成本** | 所有 Agent 今日 LLM 调用成本合计（USD） | 金额 + 预算进度条 | 5min |
| **当前 P95 延迟** | 所有 Agent 最近 5 分钟 P95 端到端延迟 | 毫秒数 + 趋势小图 | 30s |
| **全局错误率** | 最近 1 小时失败请求数 / 总请求数 | 百分比 + 趋势线 | 1min |

### 2.2 二级指标：Agent 级别详情

每个 Agent 独立展示以下指标，以卡片形式排列，支持排序和筛选。

#### 2.2.1 可用性与可靠性

| 指标 | 定义 | 目标值 | 告警阈值 |
|-----|------|-------|---------|
| **可用率** | 成功响应数 / 总请求数（按 5 分钟窗口） | >= 99.5% | < 99% 红色告警 |
| **错误率** | 5xx 错误数 / 总请求数 | < 1% | > 2% 告警 |
| **超时率** | 超过 SLA 的请求数 / 总请求数 | < 0.5% | > 1% 告警 |
| **重试率** | 触发重试的请求数 / 总请求数 | < 5% | > 10% 告警 |
| **连续失败次数** | 最近连续失败的请求次数 | 0 | >= 3 次立即告警 |

#### 2.2.2 延迟性能

| 指标 | 定义 | 目标值 | 告警阈值 |
|-----|------|-------|---------|
| **P50 延迟** | 端到端响应时间中位数 | 取决于场景 | 超过基线 50% |
| **P95 延迟** | 95 分位响应时间 | < 5s（简单）/ < 30s（复杂） | 超过 SLA |
| **P99 延迟** | 99 分位响应时间 | < 10s / < 60s | 超过 SLA 2 倍 |
| **首 Token 延迟（TTFT）** | 从请求发出到收到第一个 token 的时间 | < 500ms | > 2s |
| **Token 生成速率** | 输出 token 数 / 生成耗时（tokens/s） | > 30 t/s | < 10 t/s |
| **队列等待时间** | 请求在队列中的等待时间 | < 100ms | > 1s |

#### 2.2.3 成本指标

| 指标 | 定义 | 目标值 | 告警阈值 |
|-----|------|-------|---------|
| **每请求平均成本** | 总成本 / 请求数 | 按 Agent 设定基线 | 超过基线 200% |
| **输入 token 总量** | 今日所有请求的输入 token 合计 | 仅监控趋势 | 异常波动 |
| **输出 token 总量** | 今日所有请求的输出 token 合计 | 仅监控趋势 | 异常波动 |
| **成本/质量比** | 成本 / 质量评分 | 越低越好 | 趋势恶化 |
| **日预算消耗率** | 已消耗预算 / 日预算总额 | < 80% by EOD | > 90% 提前告警 |
| **无效调用成本** | 因错误/重试浪费的成本 | < 总成本 2% | > 5% 告警 |

#### 2.2.4 质量指标

| 指标 | 定义 | 目标值 | 告警阈值 |
|-----|------|-------|---------|
| **任务完成率** | 用户任务成功完成数 / 总任务数 | > 95% | < 90% |
| **用户满意度（CSAT）** | 用户主动反馈好评率 | > 4.0/5.0 | < 3.5 |
| **幻觉率** | 被检测到的事实错误数 / 总响应数 | < 2% | > 5% |
| **工具调用成功率** | 工具调用成功数 / 总调用数 | > 98% | < 95% |
| **响应相关性评分** | LLM-as-judge 评估的相关性均分 | > 4.0/5.0 | < 3.5 |
| **输出格式合规率** | 符合预期格式的响应数 / 总响应数 | > 99% | < 97% |
| **人工干预率** | 需要人工介入的比例 | < 3% | > 8% |

### 2.3 三级指标：请求级别追踪

支持在仪表盘中搜索和查看单次请求的完整链路：

| 维度 | 记录内容 |
|-----|---------|
| **请求元信息** | 请求 ID、时间戳、来源用户/系统、Agent 名称 |
| **输入详情** | 用户输入、系统提示词、上下文 token 数 |
| **LLM 调用链** | 每次 LLM 调用的模型、输入/输出 token、延迟、成本 |
| **工具调用链** | 工具名称、入参、返回值、耗时 |
| **中间推理** | 思考过程（如适用）、决策节点 |
| **最终输出** | 响应内容、格式、质量评分 |
| **端到端延迟分解** | 阶段耗时瀑布图：排队 → LLM 调用 → 工具执行 → 后处理 |
| **错误详情** | 错误类型、堆栈、重试次数、最终结果 |

## 4. 告警规则设计

### 4.1 告警分级

| 级别 | 触发条件 | 通知方式 | 响应时效 |
|-----|---------|---------|---------|
| **P0 - 紧急** | Agent 完全不可用（可用率 < 50% 持续 2 分钟）| 电话 + 即时通讯 + 短信 | 5 分钟内响应 |
| **P1 - 严重** | 错误率 > 5% 或 P95 延迟超 SLA 2 倍 | 即时通讯 + 邮件 | 15 分钟内响应 |
| **P2 - 警告** | 错误率 > 2% 或成本异常（超基线 200%）| 即时通讯 | 1 小时内响应 |
| **P3 - 提醒** | 质量评分下降、预算消耗加速 | 邮件 + 日报 | 下一工作日 |

### 4.2 具体告警规则

```yaml
alert_rules:
  # 可用性告警
  - name: agent_down
    condition: success_rate < 50% for 2m
    severity: P0
    channels: [phone, im, sms]

  - name: high_error_rate
    condition: error_rate > 5% for 5m
    severity: P1
    channels: [im, email]

  - name: elevated_error_rate
    condition: error_rate > 2% for 10m
    severity: P2
    channels: [im]

  # 延迟告警
  - name: latency_critical
    condition: p95_latency > sla * 2 for 5m
    severity: P1
    channels: [im, email]

  - name: latency_warning
    condition: p95_latency > sla * 1.5 for 10m
    severity: P2
    channels: [im]

  # 成本告警
  - name: cost_spike
    condition: avg_cost_per_request > baseline * 3 for 15m
    severity: P2
    channels: [im]

  - name: budget_exhaustion
    condition: daily_budget_consumed > 90%
    severity: P2
    channels: [im, email]

  - name: budget_exhaustion_critical
    condition: daily_budget_consumed > 95%
    severity: P1
    channels: [im, email]

  # 质量告警
  - name: quality_degradation
    condition: quality_score < 3.5 for 1h
    severity: P2
    channels: [im]

  - name: hallucination_spike
    condition: hallucination_rate > 5% for 30m
    severity: P1
    channels: [im, email]

  # 异常检测
  - name: request_volume_anomaly
    condition: request_volume deviation > 3sigma for 15m
    severity: P3
    channels: [email]
```

### 4.3 告警抑制与聚合

- **关联抑制**：Agent-down 告警触发时，自动抑制该 Agent 的延迟/错误率告警
- **告警聚合**：同一 Agent 同类告警 5 分钟内合并为一条
- **静默窗口**：支持配置维护窗口，暂停非 P0 告警
- **告警升级**：P1 告警 15 分钟无人响应自动升级到 P0

## 6. 质量评估方案

### 6.1 自动化质量评估

| 评估维度 | 方法 | 频率 | 覆盖率 |
|---------|------|------|-------|
| **格式合规** | 规则校验（JSON schema、正则） | 每个请求 | 100% |
| **工具调用正确性** | 工具返回码 + 结果验证 | 每次调用 | 100% |
| **响应相关性** | LLM-as-Judge（轻量模型） | 采样 10% | 10% |
| **事实准确性** | LLM-as-Judge + RAG 检索验证 | 采样 5% | 5% |
| **安全性** | 内容安全分类器 | 每个请求 | 100% |
| **用户满意度** | 显式反馈（点赞/点踩） | 用户触发 | ~5% |

### 6.2 质量评分公式

```
Agent 质量分 = (
    格式合规率 * 0.1 +
    工具调用成功率 * 0.2 +
    响应相关性均分/5 * 0.3 +
    事实准确率 * 0.2 +
    安全通过率 * 0.1 +
    用户满意度均分/5 * 0.1
) * 100
```

## 7. 成本建模与优化

### 7.1 成本分解模型

```
单次请求成本 = LLM 调用成本 + 工具调用成本 + 基础设施成本

LLM 调用成本 = Σ(输入token数 * 输入单价 + 输出token数 * 输出单价 - 缓存token折扣)
工具调用成本 = Σ(外部API调用费)
基础设施成本 = (计算资源 + 存储 + 网络) / 总请求数
```

### 7.2 成本优化监控指标

| 优化方向 | 监控指标 | 目标 |
|---------|---------|------|
| **Prompt 缓存** | 缓存命中率、缓存节省金额 | > 30% 命中率 |
| **模型选择** | 各模型使用比例、成本/质量比 | 简单任务用小模型 |
| **上下文压缩** | 平均上下文长度趋势 | 持续优化 |
| **批量处理** | 批量请求比例、批量节省金额 | 适用场景 100% 批量化 |
| **重试控制** | 重试率、重试浪费金额 | < 5% |

## 8. 实现路线图

### Phase 1（第 1-2 周）：基础可观测性

- [ ] 统一日志格式，所有 Agent 接入结构化日志
- [ ] 部署 Prometheus + Grafana 基础设施
- [ ] 实现一级指标（全局概览）仪表盘
- [ ] 配置 P0/P1 告警规则
- [ ] 建立请求级别 trace_id 透传

### Phase 2（第 3-4 周）：Agent 级别监控

- [ ] 实现二级指标（Agent 卡片）仪表盘
- [ ] 接入 ClickHouse 存储历史数据
- [ ] 实现请求级别下钻功能
- [ ] 配置 P2/P3 告警规则

## 10. 运维最佳实践

### 10.1 仪表盘使用规范

- **每日巡检**：运营人员每天 9:00 检查全局健康评分，低于 80 分触发排查
- **成本周会**：每周回顾各 Agent 成本趋势，识别优化机会
- **质量月报**：每月分析质量趋势，制定改进计划
- **容量规划**：基于请求量趋势，提前规划扩容

### 10.2 基线管理

- 每个 Agent 的指标基线每周自动更新（使用过去 4 周同期数据）
- 基线更新前需人工确认，避免异常数据污染基线
- 大版本发布后触发基线重算

### 10.3 事件关联

- 部署事件自动标记在时间轴上，便于关联指标变化
- 外部依赖故障（如 LLM Provider 宕机）自动标注
- 支持手动添加事件标注（如营销活动、配置变更）

## 11. 扩展性考虑

- **新 Agent 接入**：统一埋点 SDK，新 Agent 只需引入 SDK 并配置 agent_id，自动出现在仪表盘
- **多环境支持**：通过 `environment` 标签区分 prod/staging/dev
- **多区域支持**：通过 `region` 标签区分部署区域
- **自定义指标**：支持各 Agent 注册自定义业务指标（如 "文档解析准确率"）
- **API 访问**：仪表盘数据通过 API 暴露，支持嵌入到其他内部系统
