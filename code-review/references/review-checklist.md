# 代码审查清单

本文档是代码审查的结构化检查清单，供 `/code-review` 技能执行审查时参考。按维度分类，每个检查项包含判断标准和典型问题模式。

## 一、正确性检查

### 1.1 逻辑正确性

- [ ] **条件判断**：`if/else` 分支覆盖所有情况，逻辑运算符（`&&`/`||`）优先级正确
- [ ] **循环边界**：数组索引不越界，循环终止条件正确
- [ ] **短路求值**：依赖短路行为的表达式顺序正确
- [ ] **空值处理**：所有可能为 null/undefined/None 的值都已检查
- [ ] **类型安全**：无隐式类型转换导致的意外行为

```python
# 问题：短路求值顺序错误
if obj.method() and obj is not None:  # obj 可能为 None 时 method() 已崩溃
    pass

# 修正
if obj is not None and obj.method():
    pass
```

### 1.2 错误处理

- [ ] **异常捕获范围**：不使用裸 `except`/`catch`，捕获具体异常类型
- [ ] **资源释放**：文件、连接、锁等资源在异常路径也能正确释放
- [ ] **错误传播**：异常信息不丢失，包含足够的上下文
- [ ] **重试逻辑**：重试有上限，有退避策略，不重试不可重试的错误

```python
# 问题：裸 except 吞掉所有异常
try:
    result = process()
except:
    pass  # KeyboardInterrupt, SystemExit 也被吞掉

# 修正
try:
    result = process()
except (ValueError, TypeError) as e:
    logger.error(f"Processing failed: {e}")
    raise
```

### 1.3 并发安全

- [ ] **共享状态**：多线程/协程访问的共享变量有保护机制
- [ ] **死锁预防**：锁的获取顺序一致，有超时机制
- [ ] **竞态条件**：检查-执行（check-then-act）操作是原子的

## 二、安全性检查

### 2.1 注入防护

- [ ] **SQL 注入**：使用参数化查询，不拼接 SQL 字符串
- [ ] **XSS**：用户输入在 HTML 输出前已转义
- [ ] **命令注入**：不将用户输入拼接到 shell 命令
- [ ] **路径遍历**：文件路径参数已验证不包含 `..`

```python
# 问题：SQL 注入
query = f"SELECT * FROM users WHERE id = {user_id}"

# 修正
query = "SELECT * FROM users WHERE id = %s"
cursor.execute(query, (user_id,))
```

### 2.2 认证与授权

- [ ] **权限检查**：敏感操作前验证用户权限
- [ ] **越权访问**：用户不能访问/修改其他用户的资源（IDOR）
- [ ] **Token 安全**：JWT 验证签名、过期时间、issuer

### 2.3 敏感数据

- [ ] **无硬编码密钥**：密码、API Key 不在代码中
- [ ] **日志脱敏**：日志不包含密码、Token、身份证号等
- [ ] **传输加密**：敏感数据不在 HTTP 明文传输

## 三、性能检查

### 3.1 算法复杂度

- [ ] **嵌套循环**：O(n²) 或更高的操作是否有优化空间
- [ ] **数据结构选择**：查找操作是否使用了合适的数据结构（dict vs list）

```python
# 问题：O(n²) 查找
for user in users:
    if user.id in [u.id for u in target_list]:  # 每次遍历 target_list
        result.append(user)

# 修正：O(n)
target_ids = {u.id for u in target_list}
for user in users:
    if user.id in target_ids:  # O(1) 查找
        result.append(user)
```

### 3.2 数据库性能

- [ ] **N+1 查询**：循环中不执行数据库查询
- [ ] **索引使用**：WHERE/JOIN 条件的字段有索引
- [ ] **批量操作**：多次单条操作改为批量操作
- [ ] **SELECT 字段**：不使用 `SELECT *`，只查询需要的字段

### 3.3 内存与资源

- [ ] **大对象处理**：大文件使用流式处理，不一次性加载
- [ ] **缓存利用**：重复计算的结果是否可以缓存
- [ ] **连接池**：数据库/HTTP 连接使用连接池

## 四、可维护性检查

### 4.1 命名与可读性

- [ ] **变量命名**：名称能自解释，不使用单字母（循环变量除外）
- [ ] **函数命名**：动词开头，清晰表达行为（`get_user`, `create_order`）
- [ ] **魔法数字**：硬编码数字提取为命名常量
- [ ] **注释必要性**：复杂逻辑有注释说明"为什么"，而非"做什么"

```python
# 问题：魔法数字
if retry_count > 3:
    raise Error()

# 修正
MAX_RETRY_COUNT = 3
if retry_count > MAX_RETRY_COUNT:
    raise Error()
```

### 4.2 结构与设计

- [ ] **函数长度**：单函数不超过 50 行（超过考虑拆分）
- [ ] **职责单一**：一个函数/类只做一件事
- [ ] **重复代码**：相似逻辑提取为公共函数
- [ ] **依赖方向**：高层模块不依赖低层实现细节

### 4.3 接口设计

- [ ] **参数数量**：函数参数不超过 4 个（超过使用对象/结构体）
- [ ] **返回值一致**：函数返回类型/结构保持一致
- [ ] **向后兼容**：公共 API 变更不破坏现有调用方

## 五、测试覆盖检查

### 5.1 测试存在性

- [ ] **新功能有测试**：每个新功能有对应的单元测试
- [ ] **Bug 修复有测试**：修复的 bug 有回归测试防止复发
- [ ] **边界条件**：测试覆盖空值、零值、最大值、最小值

### 5.2 测试质量

- [ ] **断言明确**：测试有具体的断言，不只检查"不报错"
- [ ] **测试独立**：测试之间无依赖，可单独运行
- [ ] **Mock 合理**：外部依赖被 Mock，但不过度 Mock

## 六、Git 与提交检查

- [ ] **提交粒度**：每个提交是逻辑上完整的变更单元
- [ ] **提交信息**：遵循 Conventional Commits 规范
- [ ] **敏感信息**：`.env`、密钥文件未被提交
- [ ] **文件大小**：无大型二进制文件被提交

## 审查输出严重性定义

| 级别 | 标记 | 含义 | 处理要求 |
|------|------|------|----------|
| Critical | 🔴 | 会导致崩溃、数据丢失、安全漏洞 | 必须修复后才能合并 |
| Major | 🟠 | 影响功能正确性或性能 | 强烈建议修复 |
| Minor | 🟡 | 影响代码质量或可维护性 | 建议修复，可后续处理 |
| Suggestion | 🔵 | 改进建议，非必须 | 可选采纳 |

## 审查报告检查

审查完成后，确认报告包含：
- [ ] 每个问题标注了文件路径和行号
- [ ] 每个问题说明了"为什么"是问题
- [ ] 每个问题提供了修复建议或示例代码
- [ ] 严重性分级合理（不夸大也不遗漏）
- [ ] 列出了代码中的亮点（做得好的地方）
