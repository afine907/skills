# 验收标准 (Acceptance Criteria) 编写指南

## 什么是验收标准？

验收标准是用户故事的"完成定义"，明确告诉开发和测试：什么情况下这个故事算"做完了"。

## 两种主流格式

### 1. Given-When-Then 格式（推荐）

```gherkin
Given {前置条件/上下文}
When {用户操作/触发事件}
Then {期望结果/系统响应}
```

**示例**：
```gherkin
Given 用户已登录且余额为 100 元
When 购买价格为 80 元的商品
Then 扣款成功，余额变为 20 元
And 生成订单记录
And 发送购买成功通知
```

### 2. 验证清单格式

```markdown
- [ ] 输入有效邮箱，注册成功
- [ ] 输入重复邮箱，提示已存在
- [ ] 输入无效邮箱，提示格式错误
- [ ] 密码少于8位，提示长度不足
- [ ] 密码不含特殊字符，提示要求
```

## 编写原则

### 1. 覆盖三类场景

| 场景类型 | 说明 | 示例 |
|----------|------|------|
| 正常路径 | 典型成功场景 | 正确输入 → 成功 |
| 边界条件 | 边界值和极端情况 | 空输入、最大长度 |
| 异常路径 | 错误和异常处理 | 网络超时、权限不足 |

### 2. 具体可测

| ❌ 模糊 | ✅ 具体 |
|---------|---------|
| 系统应该快 | 页面加载时间 < 2秒 |
| 用户可以搜索 | 支持按名称、邮箱搜索，结果分页显示 |
| 有错误提示 | 提示"邮箱格式不正确"，输入框标红 |

### 3. 从用户视角

| ❌ 技术视角 | ✅ 用户视角 |
|-------------|-------------|
| 调用 API 返回 200 | 看到"保存成功"提示 |
| 数据库插入记录 | 新记录出现在列表中 |
| 触发消息队列 | 收到邮件通知 |

### 4. 独立可验证

每条验收标准应该能独立测试，不依赖其他标准的执行结果。

## 常见错误

### ❌ AC 包含实现细节
```markdown
- Given 数据库中 users 表有一条记录
- When 前端发送 POST 请求到 /api/users
- Then 后端返回 JSON 并存入 Redis
```

### ✅ AC 使用用户语言
```markdown
- Given 我已注册账号
- When 点击"修改昵称"并输入新昵称
- Then 昵称更新成功，页面显示新昵称
```

### ❌ AC 过于宽泛
```markdown
- 系统应该安全
- 性能要好
```

### ✅ AC 具体明确
```markdown
- 密码传输使用 HTTPS 加密
- 敏感操作需要二次验证
- 列表页加载时间 < 1秒（1000条数据）
```

## 数量指导

- 每个用户故事 **3-5 条**验收标准为宜
- 最少 2 条（正常路径 + 1条异常/边界）
- 最多不超过 8 条（超过则考虑拆分故事）
